# 全 issue 验收手册

本文件为仓库全部 50 个 issue 的验收操作说明。每条给出：**验收方式**（命令 / 测试 / computer-use 交互）、**操作步骤**、**通过标准**。

## 0. 通用约定

### 0.1 验收环境准备

```bash
npm install
npm run typecheck   # 任何实施类 issue 验收前先跑
npm test            # 全量测试必须绿
```

真实 LLM 验收需二选一：

- `KIMI_API_KEY=<key>` 环境变量；
- 或先跑一次 `kimi` 让 `~/.kimi-code/credentials/kimi-code.json` 里有未过期 OAuth token。

无 key 环境用 `FAKE_LLM=1`（FakeLLM 预置脚本流）做功能性验收。

### 0.2 computer-use（CU）验收通用流程

TUI 类 issue 的交互验收用 kimi-cu 工具，标准流程：

1. 在一个可见终端窗口（Windows Terminal / conhost）里启动 TUI：`npm run dev`（或 `FAKE_LLM=1 npm run dev`）。
2. `list_apps` / `list_windows` 找到终端窗口，`activate_window` 置前。
3. `get_app_state`（含截图）确认渲染内容。
4. 用 `type_text` / `press_key` 模拟输入与键位，`click` 仅在确有需要时用。
5. 每个关键动作后重新 `get_app_state` 截图，对照通过标准逐项核对。
6. 验收结束 `turn_ended` 收尾。

> 注意：CU 截图验证的是「真实终端里的最终表现」，VirtualTerminal 测试验证的是「渲染逻辑」。两者不互相替代——实施票要求两者都过。

### 0.3 决策 / 调研 / 原型票的验收通则

这三类不写产品代码，验收标准是「产出物存在且能指导下游」：

- **决策票**：结论以评论或 ADR 落盘，明确回答 issue 里列的每个待定点；被它 block 的下游 issue 能引用结论开工。
- **调研票**：回答 issue 的 Question，附证据（源码行号 / 实测记录），不泄露 token。
- **原型票**：有可运行的原型 + 真人试用反应记录链接到 issue。

### #25 审批：分级规则引擎

**方式**：测试为主。

### #26 审批：会话级「始终允许」记忆

**方式**：测试 + CU。

### #27 审批：`-p` 模式 `--yes` 放行策略

**方式**：命令。

```bash

npm run agent -- -p --yes "写一个文件 x.txt"    # 预期：放行
npm run agent -- -p --yes "删除系统目录"        # 预期：危险 pattern 仍被规则引擎拦截
```

三种行为均符合 #5 结论即通过。
